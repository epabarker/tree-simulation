# M13: where a season's time goes, and golden-safe speed-ups

## Question
Where does the worker spend a season, and how much of that can be saved without changing a single result? The M12 review planned a target of ≤ 12 ms a season on desktop for the ring presets. It quoted 25–40 ms, a figure taken from the page and the CLI, which also count metrics and CSV output.

"Without changing a result" means bit-identical. `hashWorld` hashes every Float64 column, so the goldens, and the benchmark's own 100-season hash per case, prove it.

## Setup
```bash
npm run bench                                   # six cases, 100 seasons, best of 3, full snapshots
npm run bench -- --snapshot lean                # snapshots as the home page will ask for them
npm run bench -- --compare runs/bench/805faeb.json
```
`cli/bench.ts` runs each case as the worker does: one season, then a `SnapshotBuilder.build`. `runSeason` reports the end of each phase through an optional `PhaseMark` callback, and the core still reads no clock.

**Cases:**
- `skyTree`, `skyStand`, `coniferStand`, `thinning` and `forest`;
- `wideForest`: the forest on a 420-cell ring with 20 trees.

**Machine:** Intel i7-1260P, Node 24.18. Baseline at `805faeb`, after at `702e810`. The CPU profiles came from `node --cpu-prof`.

**What changed:**
1. **The sky sweep is bounded to the leafy rows.**
   - Rows above the highest leafy row have optical depth exactly 0 in every direction. They are filled with the open-sky sums, added in the same order a cell would add them.
   - `Math.exp` is skipped where the depth is 0, because exp(−0) = 1 exactly.
2. **Periodic laps stop at the fixed point.** A lap of the shallow sweep around the ring is a fixed map of the whole field, so once a lap changes nothing, every later lap would change nothing either. On `forest`, the 15° direction stops after 5 of its 8 laps, and 40° after 3 of 4.
3. **Wrapping without modulo** in the sweep's inner loops: one add or subtract, since a step crosses at most one width. This gave 1.27× on the rings by itself.
4. **Junction exponents by Newton's method.** f(Δ) = Σ xᵢ^Δ − 1 is convex and falling, so Newton started left of the root climbs to it without overshooting. Child chains replace the per-node arrays.
   - The result is the same set of junctions, within 1e-13 of the old bisection, on `forest`, `coniferStand`, `troll` and `skyTree` at season 80.
   - It is 5–13× faster (11.1 → 0.9 ms for 2903 junctions in a conifer stand).
5. **Snapshot options:** junctions and field can be switched off; the home page will need neither. The worker reports `snapshotMs`, and the HUD's worker time now includes it.
6. **Fewer allocations:**
   - `Table` caches its column list (`add` used to call `Object.values` for every row) and reuses its compaction map.
   - `crownTopLight` sorts a typed scratch array (same order, so the same quantile).
   - `runSeason` builds its live list without `filter`.

**Planned but skipped**, because the profile did not justify them:
- `tipX`/`tipY` caching (1.5% of samples);
- `World.isRemoved` (it runs only for trees not yet planted);
- O4's `trees.some` seed check (not in the profile);
- R5's per-shoot object spread.

**Where the time goes now:** for `forest` and `coniferStand` together, `sweep` takes 30% of samples and the exp pass in `compute` 19%. Nothing else exceeds 5%.

**Test strength (for the review):** the sweep now keeps state from one season to the next (`top` and the depth buffer). A mutant that forgot to clear the row above the foliage failed only 1 of the 26 goldens (`weeping`) and none of `sky.test.ts` or `forest.test.ts`. A new unit test covers it: a sweep reused after a taller season must give exactly the field of a fresh one.

## Conclusion
- Every case is well inside the 12 ms target. The rings went from 12.4 to 3.8 ms, and the double-width ring takes 7.2 ms.
- The light field is now most of what is left: about 70% on the rings. The rest of a season is spread thin.
- The next real gains need behaviour changes and belong to M18: a row-marched shallow sweep with no laps and no strided access, then Float32 or a transmission table if the profile still points there.
- For the home page, the simulation's cost is no longer the constraint. A lean snapshot costs 0.1–0.3 ms, so phone smoothness is about the renderer (M15).
