# Analytical Review of `epabarker/tree-simulation`

## Executive summary

`epabarker/tree-simulation` has moved well beyond a small procedural-graphics experiment. Its stated goal is to generate recognisable tree form through self-organisation: buds compete for light, resources are distributed according to Borchert–Honda-style rules, poorly lit branches are shed, stems thicken through a pipe model, and neighbouring trees interact through a shared light field. The active development branch, `3d-port`, now grows trees in a 64-cell-deep three-dimensional slab while retaining a flat orthographic visual treatment, with the simulation core migrated from TypeScript to Rust/WASM and the original 2D implementation preserved at `golden-2d-ts`. citeturn357095view0turn314128view4turn572697view2

The project is unusually mature in its internal engineering discipline for a small experimental simulator. It has explicit architectural decision records, a principle-level scientific specification, a detailed milestone roadmap, deterministic keyed randomness, native and WASM execution from the same Rust core, replayable runs, golden outputs, performance measurements, a CI pipeline, automated releases and an extensive empirical calibration apparatus. The active branch's `npm run check` builds WASM, runs Rust formatting/clippy/tests, TypeScript linting/typechecking and Vitest; the repository also preserves a separate CI job that checks the archived 2D implementation against its historical goldens. citeturn838317view2turn314128view1turn838317view4

As of **6 November 2026**, the main development risk is no longer lack of implementation. It is *convergence*: keeping documentation, branch structure, validation and model scope aligned while the simulator changes quickly. Garden `v0.16.0` was released on 6 November, after PRs #48 and #49 were merged into `3d-port`; PR #50 is open with a reduced recruitment cap and reports a green 99-test check. The public issue tracker shows zero open issues, while planning and defects are being managed primarily through PRs, STATUS, ADRs, experiment notes and the roadmap instead. citeturn572697view0turn293884view4turn293884view3turn572697view1turn119104view1

The shortest path to a clearly successful next release is therefore **not another large biological mechanism**. It is to stabilise the 3D line, remove documentation/branch ambiguity, close the test gap around the Python calibration stack, turn the most important known user-visible defects into regressions, and then tackle one species-fidelity problem at a time. The project already identifies the immediate modelling target: young-tree form, the "flat cap" problem and birch's thin-pole behaviour; the current STATUS explicitly says that the direction is for trees to look both like trees and like their species, with species chosen by data. citeturn838317view1turn293884view3turn572697view3

My recommended sequence for a 1–3-person team is approximately **5–9 person-days to reach a stable v0.17-quality baseline**, followed by **5–10 additional person-days** for a tightly scoped species-validation milestone. The first phase should be mostly engineering and calibration hygiene, not algorithm expansion. The greatest technical risks are model overfitting to hand-picked visual traits, regression from highly coupled species parameters, memory/runtime growth in long-lived garden worlds, and a widening gap between current `3d-port` reality and the repository's default-branch/documentation story. citeturn293884view4turn838317view1turn784081view0

## Project goal, scientific approach and architecture

The project began as a genuinely planar interpretation of Pałubicki et al.'s self-organising tree model, with a shared 2D light grid, Borchert–Honda allocation, weighted shoot direction, self-pruning and pipe-model girth. The original specification explicitly framed these as a six-principle minimal core, with carbon balance, physiological age, mechanics, release and stand dynamics layered on as refinements. citeturn338395view0

That foundation is directly traceable to Pałubicki et al. 2009, whose model argues that realistic tree form can emerge from competition among buds and branches for light or space combined with internal signalling. The paper's central contribution is precisely the combination that this repository adopts: local branching geometry, external competition and internal regulation, rather than a purely recursive tree grammar. citeturn470231search0turn470231search10

The important strategic change is ADR 0024. The project concluded that trees growing in a plane looked too much like fans, and moved growth into a 3D slab while deliberately retaining the garden's frontal orthographic illustration. The accepted design uses a width × height × depth world, depth `D = 64`, periodic horizontal boundaries and an open depth dimension with configurable face transmission. The light model is a row-marched Beer–Lambert sweep implemented in Rust and compiled to WASM. citeturn572697view2

The active architecture cleanly separates simulation from presentation. The Rust `tree-core` package is the authoritative model; the web worker calls it through a WASM wrapper, while the CLI calls the same core natively. TypeScript owns host-facing data, browser integration, visualisation and controls. The architecture documentation states that the page, CLI, benchmarks, tests and opening forests all use the same core build. citeturn838317view2

The scientific scope is broader than Pałubicki's graphics model. Carbon production and maintenance close a size-cost feedback loop; physiological age controls architecture; mechanics introduce sag, posture and stress-driven girth; dormancy/release and shade avoidance model recovery and competitive response; and stand dynamics add recruitment, mortality and gap processes. Many of these mechanisms are explicitly linked in the spec to functional-structural plant modelling literature rather than being presented as purely graphical tricks. citeturn338395view0turn838317view0

## Comparison with academic and open-source tree simulators

The closest intellectual comparison is Pałubicki et al. 2009 itself. That model is aimed primarily at realistic image synthesis and demonstrates how competition among buds/branches and internal resource signalling can generate plausible whole-tree forms. `tree-simulation` remains recognisably within that lineage, particularly in its use of light competition and Borchert–Honda-style allocation, but has expanded the approach into explicit carbon, biomechanics, stand dynamics, species calibration and a real-time web product. citeturn470231search0turn338395view0

The repository therefore sits between **procedural graphics** and **functional-structural plant modelling (FSPM)**. LIGNUM, for example, represents a tree as structural units—segments, branching points and buds—and connects the 3D structure to metabolism on an annual timestep. That is conceptually close to this repository's metamer graph plus carbon accounting, but LIGNUM's raison d'être is physiological/tree-growth research, whereas `tree-simulation` still makes modelling choices partly to preserve responsiveness, visual recognisability and interactive control. citeturn470231search3turn470231search4turn338395view0

AMAPsim lies still further toward botanical architecture. Its published purpose is to generate detailed 3D plant architectures from explicit botanical concepts such as physiological age and reference axes, and to permit coupling with external functional models. `tree-simulation` borrows the idea of physiological age, but deliberately retains more emergence: global crown form is intended to arise from local light/resource/mechanical feedback rather than being fully specified by a botanical architectural template. citeturn147600search20turn147600search25turn338395view0

OpenAlea's L-Py is a useful software comparison rather than a direct model comparison. L-Py is an open-source L-system environment that combines formal plant rewriting with Python and interoperates with the wider OpenAlea platform. `tree-simulation` is much narrower but more vertically integrated: its simulation, renderer, garden product, calibration machinery and reference-data workflow are all designed around one model. L-Py's strength is extensibility and model composition; `tree-simulation`'s strength is a tightly reproducible end-to-end artefact. citeturn470231search5turn470231search6

GroIMP represents the mature platform end of the spectrum: it supports growth grammars, interactive 3D modelling, multiple representations and a spectral light model. Compared with that, `tree-simulation` intentionally has a smaller model/runtime surface and uses a purpose-built slab light field rather than a general spectral/raytracing environment. That choice substantially simplifies browser deployment and deterministic batch experiments, but naturally limits ecological/light realism. citeturn470231search7turn470231search8turn572697view2

Space-colonisation models are another relevant contrast. Runions, Lane and Prusinkiewicz's algorithm generates realistic branching by letting a skeleton colonise points in available space. It is excellent at spatially plausible crown filling, but the driving variable is empty-space occupation rather than explicit light production, physiological allocation, maintenance cost or branch mortality. `tree-simulation` is therefore considerably more mechanistic in its feedback loops, although space colonisation can produce visually convincing geometry with far fewer biological parameters. citeturn147600search1turn147600search3

Finally, there is a direct open-source C++ implementation of Pałubicki's ideas, `bernardosulzbach/self-organizing-tree-models`. Its stated aim is to implement the main ideas of the 2009 paper and document them clearly. Relative to that project, `epabarker/tree-simulation` is less useful as a minimal reference implementation but much more ambitious as a continuing experimental platform, with browser execution, Rust/WASM, replay, CI, empirical species fitting and stand dynamics. citeturn470231search9turn838317view2

The best way to characterise the current project is therefore: **Pałubicki-style emergent tree graphics evolving toward a compact FSPM, with unusually strong reproducibility and deployment engineering**. Its main divergence from mature research FSPMs is that many parameterisations remain pattern-calibrated or phenomenological rather than independently validated physiological measurements; the roadmap itself explicitly distinguishes settled parameters, qualitative values and species parameters still awaiting calibration. citeturn838317view0turn784081view0

The critical acceptance principle is that **validation should become progressively more independent of tuning**. The repository's M28 direction is already correct: compare model descriptors with measured/reference trees and require fresh-seed or held-out performance. The danger is that a rich parameter set can fit one set of crown descriptors while producing implausible behaviour elsewhere. The project's own recent evidence demonstrates this: broadleaf irregularity dramatically improved some regularity descriptors, but simultaneously worsened young-tree bole form, all-tree H/D and some stand survival metrics. citeturn572697view3turn293884view4

The largest technical risk is parameter coupling. PR #49 notes, for example, a hornbeam value where a change of roughly ±0.01 can flip crown behaviour, and reports trade-offs among height, garden composition, H/D and floor-light gates. That is a warning that some "species parameters" may currently compensate for model-structure deficiencies. Sensitivity analysis around accepted parameter sets would therefore deliver more scientific value than another optimisation round with additional free parameters. citeturn293884view4

A second risk is computational growth. The 3D port creates far more metamers than the old 2D model, and memory measurements directly influenced the decision to lower the garden's maximum plate width to 170. The architecture is already efficient—Rust, SIMD, WASM, worker isolation, reused buffers and compact snapshots—but long-run population dynamics can still increase memory through biological state rather than renderer overhead. Reproducible fresh-process budget tests should become a release gate. citeturn572697view2turn293884view4

A third risk is research/product entanglement. The same core supports a scientific lab, calibration scripts and a visually polished website garden. That is a strength, but the product can favour visually attractive compromises that are not biologically well validated, while scientific calibration can introduce complexity that does not visibly improve the garden. The current STATUS's rule—no new descriptor, registration, ADR or audit without a reason visible in the garden—is a useful scope-control device, but it should be complemented by the inverse rule: no visual fix should be described as biological validation unless it passes an independent quantitative gate. citeturn838317view1
